2. Readiness is a LEVEL with reasons on every pod (/readyz on port {{ .Values.ports.observability }}).
   Metadata pods report Ready before a Raft leader exists — by design. Data
   pods stay NOT READY until the metadata exchange below finds their range.

vtop {{ .Chart.AppVersion }} — {{ int .Values.replicaCount }} co-located node(s) as StatefulSet {{ $fullname }}.

1. Watch the pods come up:

     kubectl -n {{ $ns }} get pods -l app.kubernetes.io/instance={{ .Release.Name }},app.kubernetes.io/name={{ include "vtop.name" . }} -w

2. Readiness is a LEVEL with reasons, not a startup marker. /readyz on port
   {{ .Values.ports.observability }} answers 200 "ready" or 503 "not ready: <reason>", and on a
   co-located node it is the CONJUNCTION of both roles. Read the reason:

     kubectl -n {{ $ns }} port-forward pod/{{ $fullname }}-0 {{ .Values.ports.observability }}:{{ .Values.ports.observability }} &
     curl -s http://127.0.0.1:{{ .Values.ports.observability }}/readyz

   Fresh pods report Ready before a Raft leader exists — that is by design
   (requiring leadership would deadlock bootstrap, which arrives over the
   admin endpoint being gated). And a node that later goes UNREADY because it
   was fenced is the system WORKING: every write sent to it is one it must
   refuse. Do not loosen the probes; read the reason.

3. Bootstrap the metadata Raft group ONCE per cluster lifetime (all nodes
   running, empty logs). Run vtopctl against any admin endpoint with an
   operator certificate signed by your cluster CA:

     kubectl -n {{ $ns }} port-forward pod/{{ $fullname }}-0 {{ .Values.ports.metaAdmin }}:{{ .Values.ports.metaAdmin }} &
     vtopctl meta init --members {{ join "," $ids }} --config admin.yaml
     vtopctl meta status --config admin.yaml

   Forward a SPECIFIC POD, not the Service. Each pod presents a certificate
   whose SAN is that pod's own headless FQDN, so a load-balanced endpoint
   gives the client no name it can verify and TLS fails before vtopctl sends
   anything. admin.yaml must therefore carry BOTH:

     endpoint: localhost:{{ .Values.ports.metaAdmin }}
     server_name: {{ $fullname }}-0.{{ include "vtop.headlessServiceName" . }}.{{ $ns }}.svc.{{ .Values.clusterDomain }}

   plus ca_cert/client_cert/client_key for your operator credentials.
   `server_name` defaults to "localhost", which will NOT match — set it.

   Node ids are pod ordinal+1: {{ $fullname }}-0 is meta node 1, and so on.

5. ONE range, every pod a CANDIDATE (#284): the role follows the metadata
   lease. After `meta init`, create the topic and register each node once —
   the range cannot be leased before metadata knows it exists, and /readyz
   stays closed on every pod until a completed metadata exchange FINDS it:

     vtopctl meta create-topic --name {{ .Values.data.range.topic }} --topic-uuid {{ .Values.data.lease.topicUuid | default "<topicUuid>" }} --root-range-uuid {{ .Values.data.range.rangeId | default "<rangeId>" }} --config admin.yaml
     # once per pod, each at its OWN headless FQDN:
     vtopctl meta register-node --node-uuid <that pod's data.nodeUuids entry> --addr <pod-fqdn>:{{ .Values.ports.replica }} --config admin.yaml

   Whichever pod acquires the range leads; when the holder dies, a surviving
   candidate takes the range in place — no re-render, no upgrade. WHICH pod
   leads is an election's outcome, so ask metadata rather than assuming:

     vtopctl --json meta range-lease --topic-uuid {{ .Values.data.lease.topicUuid | default "<topicUuid>" }} --range-uuid {{ .Values.data.range.rangeId | default "<rangeId>" }} --config admin.yaml

   and aim produce/fetch at the holder's own headless FQDN on port {{ .Values.ports.native }}.
