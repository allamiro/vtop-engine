# Commit-rule review (engine / archive plane)

The invariant: **source progress (Kafka offset, file byte offset, spool offset) never advances until the object and its manifest are durably written and verified.** Normative text: `docs/VTOP_PROTOCOL_DRAFT.md` §12-13. Implementation tour: `docs/ARCHITECTURE.md` §5, §13.

It is enforced in three layers; a change must not weaken any of them:
1. `vtop-core::state_machine` — legal transitions only.
2. `vtop-state` (`StateStore`, SQLite / Postgres) — the durable ledger refuses an illegal transition.
3. The engine pipeline in `vtop-cli` — the order of calls.

## Why this is the right shape (book lens)

This is an at-least-once pipeline made safe by idempotent, verifiable output — the end-to-end argument: the guarantee is established by the *final* check (verify the stored object against the manifest), not by any one hop being reliable. For a single in-flight range, a crash between upload and commit yields a replay, never a gap. That is conditional: replay output is not idempotent today (the batch id embeds a timestamp and random suffix, so a replay writes a new key), and with several ranges per source a FAILED range followed by a *later* committed range can leave a hole (tracked in #552). Duplicates are tolerable; loss is not. Keep that asymmetry in every decision, and make the no-gap claim explicitly conditional on stopping or fencing later commits of a source whose earlier range has not committed.

## Checklist

- [ ] **Order.** Is there any path where the source marker can advance before `VERIFIED`? Include error paths, retries, shutdown, and `recover()`.
- [ ] **Crash at every boundary.** For each state transition, what does restart do? `Engine::recover()` currently handles `Verified` (retry source commit) and `SourceCommitted` (nothing); every other non-committed state becomes `REPLAY_REQUIRED` and is replayed through the adapter's `replay_from_marker(row.progress_start)`, one row at a time. That is per-row, not "from the last committed marker": with several uncommitted ranges the rows overwrite each other's rewind, and file/spool adapters clamp the rewind to the committed point — see the failed-range item below and #552. Keep it that way unless a granular resume is proven safe (`replay.rs` `Retry*` variants are reserved, not live).
- [ ] **Verification strength is honest.** Strong vs backend-limited vs size-only (protocol §17) must be reported as what it is. A weaker check must never be logged or exported as a strong one.
- [ ] **Manifest binding.** Manifest names the exact marker range, checksum, and object location, and is self-hashed. A change to batch contents must change the manifest.
- [ ] **Idempotent replay.** Known gap: `batch_id` embeds a timestamp and random suffix, so replay writes a new key (protocol §15.1 goal not met). Don't claim deterministic naming; don't make it worse; if you close the gap, say so in docs/ARCHITECTURE.md §13.
- [ ] **A failed range must be re-driven, or the source must stop.** The read head moves at read time. If a batch goes FAILED in-process and a *later* batch of the same file/partition reaches `SOURCE_COMMITTED`, the earlier range is a permanent hole: `replay_from_marker` is only called from `recover()` at startup, and the file adapter clamps the rewind to `committed_byte`. After any FAILED outcome either rewind that source immediately (with backoff) or refuse to commit later ranges of it. On restart, replay must rewind to the *minimum* start over all uncommitted ranges, not last-row-wins.
- [ ] **Commits are monotonic.** A late commit of an older VERIFIED range (recovery retry) must not move a marker backwards. Take the max or refuse.
- [ ] **Know whether the rewind is clamped; reason about where it LANDS.** The file and spool adapters never rewind below their committed byte, so the effective restart of a stale row whose bytes a later batch already archived is the committed point, not the row's start. The Kafka adapter on `main` rewinds straight to the marker's `start_offset` (#563 clamps it to the group's committed offset) - check the adapter you are reasoning about, and never assume another's clamp. A hold-back rule (do not commit a VERIFIED range above one about to be re-read) must be evaluated on where the rewind landed, or a stale row blocks every VERIFIED range above it for ever. The adapter must also say whose position it reports: a per-path cursor describes the current file, so it answers only for a marker from that file. Rewind, then decide, then rewind again after the commits have moved the committed points.
- [ ] **A late commit is judged by the generation it was read in, not by the file as it looks now.** A copytruncate that has regrown past an old range's end is indistinguishable, by inode and length, from the file that range was read from. Track a generation per cursor (bumped on every restart-on-discontinuity) and the generation of each range handed out; settle commits against it, oldest first. Where there is no record (after a restart), fall back to the length test, and never let a stale commit drive `delete_after_commit`.
- [ ] **A restart seed carries everything the check needs.** The inode alone is not enough: the length the committed batch observed catches a truncation above the committed offset. Take the inode, the offset AND the length from the NEWEST committed row, never a maximum - a copytruncate keeps the inode, so a per-inode maximum hands the new content the old content's offset. Order "newest" by when the window was read, not by when its state last changed (recovery can commit an older window last), and compare timestamps as instants or in one fixed-width form (`.1Z` sorts after `.15Z` as text). Read u64 inodes as exact tokens, not as numbers a database can round.
- [ ] **Whatever prunes history must keep the row the seed reads.** A seed that picks the newest row and a pruner that keeps the highest offset disagree exactly after a rotation or copytruncate, and the prune deletes the restart cursor. Give both the same order (and the pruner an index for it), and assert the seed is unchanged across a prune.
- [ ] **A window commits only its last read's range.** The engine buffers several reads into one window and commits the window's `progress_end`, so any per-range bookkeeping in an adapter (generations, issued ranges) must retire the window's earlier ranges too - of the same generation only, so an older generation's late commit still finds its record.
- [ ] **A read that finds a discontinuity and then fails must still apply it.** If the adapter judges the open file truncated, then errors reading the new content (a first line over `max_bytes`), dropping the judgement leaves the old position and length; once the file regrows past that length the next read sees no truncation. Carry the judgement with the error and restart the cursor as a successful read would.
- [ ] **A fence token is released when the work ends and kept when the claim is lost.** Releasing a lost claim's token unfences the stalled writer's next attempt; bound the map instead. A claim returns the rows its own statement changed, never a re-read by owner name. The fence binds only engines that know it: drain older engines first.
- [ ] **Every `REPLAY_REQUIRED` row has an exit.** A row that stays incomplete re-triggers its rewind on every restart. Do not discard a replay error with `let _ =`; surface it.
- [ ] **The manifest is the only commit marker for an object.** Objects without a verified manifest are garbage; downstream readers discover data only through manifests. State how orphans from FAILED batches are swept.
- [ ] **Partial uploads / multipart.** An object visible in the bucket is not a verified object. Verify reads back (or uses backend checksums) before commit.
- [ ] **Poison input is a policy, not an accident.** Decide halt vs skip-to-dead-letter. One bad record at a partition head blocks everything behind it; scope the failure to that partition/file, not the topic. If skipping is allowed, the skipped bytes must themselves be archived and verified before the marker advances.
- [ ] **File identity.** Key file cursors by (device, inode, path); handle rename-rotation, copytruncate, truncation, inode reuse and a partial last line. Seeding a cursor from the ledger must not take a max across different inodes of one path.
- [ ] **Time partition is a stated choice.** Which clock picks the object partition — record event time, batch seal time, or upload time? Where do late records, backfills and replays land? Does layout depend on batch boundaries (e.g. format detection on a 1-record batch)? Manifests should carry min/max event time.
- [ ] **Operation identity.** Exactly-once needs an id generated at the origin and carried through every hop. A batch id with a timestamp/random suffix names an *attempt*, not an operation; readers then need a documented dedupe key (`source, progress_start..progress_end`, overlap rule).
- [ ] **Fleet-mode claims need a fencing token.** A `lease_until` column says who *should* write; a paused owner can still write. Every transition `UPDATE` must carry a claim generation in its `WHERE` clause, checked in the same transaction as the VERIFIED / SOURCE_COMMITTED write; compare lease expiry on the database clock.
- [ ] **Every external call has a deadline.** S3 and Postgres clients with no operation/statement timeout can hang the whole cycle with the process alive and no error. Pair with a last-successful-cycle watchdog gauge. Retries: classify idempotent first, exponential backoff with jitter, retry at one layer only.
- [ ] **Completeness, not just soundness.** `verify-manifest` proves one object matches its manifest. Also needed: every committed ledger/marker range has a verified object and ranges tile with no gaps (duplicates tolerable, holes not). Ledger pruning removes the cross-check anchor — leave a digest first.
- [ ] **New source adapter.** Implements `SourceAdapter` (`crates/vtop-adapters/src/base.rs`) and its own `ProgressMarker` variant. Reading must not advance *committed* progress; the engine calls `commit_progress(&ProgressMarker)` only after the batch is `VERIFIED`. Where the committed position lives is adapter-specific: Kafka commits the group offset to the broker (the ack must be observed), while file and spool adapters keep an in-memory cursor and the **durable record is the state-store ledger**, which seeds the cursor on restart — so the requirement is durable ledger persistence plus replay-safe recovery, not a fsync of an offset into the source file. See ARCHITECTURE §7.1 for what the commit rule does *not* cover.
- [ ] **New upload backend.** Implements the `UploadBackend` verification contract and passes `crates/vtop-upload/tests/transport_conformance.rs`.
- [ ] **State store change.** Both SQLite and Postgres go through `state_machine`; add the case to `vtop-state` `test_battery.rs` so both backends are held to it.

## Tests that prove it

Existing: `tests/integration_replay.rs`, `integration_manifest_rollback.rs`, `integration_state_recovery.rs`, `scripts/e2e-smoke.sh`, benchmark scenario `05-fault-replay.yaml`. A fix needs a test that fails against the old behaviour (see `vtop-contributing`). Prefer injecting the fault *between* two steps (after upload, before commit) over mocking the whole step.

## Review output format

Report as: invariant touched -> the interleaving that breaks it (concrete steps) -> minimal fix -> the test that would have caught it. If no interleaving breaks it, say what you checked.
